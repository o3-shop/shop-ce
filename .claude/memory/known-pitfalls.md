## Bot/Guest Request Handling
- `UtilsComponent::toCompareList()` (and similar utils methods) can crash on bot requests where session/user context is not fully initialised. Always guard with a user/session existence check before accessing user-dependent data.

## Article List Checks
- `Article::isInList()` must check both wish list and notice list independently. A missing check on one list caused a bug (fixed in eb4c3c8).

## Directory Creation
- Do not use ad-hoc `mkdir()` calls scattered through setup code. Use the centralised safe helper introduced in eb4c3c8. It handles race conditions and permission errors gracefully.

## NEVER run composer inside `testing-library/` — it clobbers the shop's vendor dir
- The satellite clone at `./testing-library/` has `vendor -> ../vendor` (symlink into the shop's vendor, created by `docker/entrypoint.sh`). Running `composer install`/`update` **inside** `testing-library/` therefore rewrites the *shop's* `vendor/` with testing-library's dependency graph as root: it deletes the `vendor/o3-shop/testing-library` symlink, prunes ~12 of shop-ce's require-dev packages (phpstan, rector, prophecy, phpdocumentor…), installs a duplicate `o3-shop/shop-ce` from GitHub into `vendor/o3-shop/shop-ce`, and dumps a full shop `source/` tree + `.env` + `composer.lock` into `testing-library/` (shop-composer-plugin post-install). Symptom: `./docker.sh test*` fails with `Error: 'runtests' command not found` (runtests lives at `vendor/o3-shop/testing-library/bin/runtests`, on the container PATH). Diagnosis: `vendor/composer/installed.php` shows `'root' => install_path '../../testing-library'` instead of `'../../'`.
- **Recovery (verified 2026-06-02, both incidents):**
  1. `docker exec -w /var/www/html <shop-container> composer install --no-interaction --no-plugins --no-scripts` — **the `--no-plugins --no-scripts` flags are required.** A plain `composer install` can die silently (exit 255, no output even with `-vvv`) at `pre-package-uninstall: OxidEsales\ComposerPlugin\Plugin->uninstallPackage` while removing the stray `o3-shop/shop-ce`: the plugin's `require vendor/autoload.php` prepends the vendor autoloader into the composer process, and vendor's `React\Promise\Promise` (v2) clashes with the composer 2.2 phar's already-loaded react/promise v1 `PromiseInterface` → fatal only visible via `php -d error_log=... /usr/local/bin/composer install`.
  2. `docker exec -w /var/www/html <shop-container> composer install --no-interaction` — normal pass; package ops are now a no-op so the plugin hooks and post-install scripts (UNC generation, test_config.yml) run cleanly.
  3. `rm -rf vendor/o3-shop/testing-library && ln -s ../../testing-library vendor/o3-shop/testing-library` (composer reinstalls the real package dir; swap it back to the satellite symlink).
  4. Delete the debris inside `testing-library/`: `source/`, `.env`, `.env.dist`, `composer.lock` (keep the `vendor` symlink).
  5. Verify: `command -v runtests` in the container; `vendor/composer/installed.php` root is `dev-b-1.6` with install_path `'/../../'`; installed.json matches composer.lock (no missing/extra); `grep Tests vendor/composer/autoload_psr4.php` shows `OxidEsales\EshopCommunity\Tests\` (NOT `OxidEsales\TestingLibrary\Tests\` — a testing-library-rooted autoload makes whole-directory phpunit runs die with exit 255 and zero output, because `ExitHandlerTestTrait` can't autoload).
- To upgrade a dependency **of testing-library** (e.g. a dependabot alert): edit `testing-library/composer.json` only and push to the testing-library repo. NEVER `composer update` inside `testing-library/` — resolution happens upstream/CI; the local satellite is consumed via symlink and the shop's composer.lock governs the actual vendor.

## `UtilsObjectTest::testOxNewClassExtendingWhenClassesDoesNotExists` fails when run in isolation (pre-existing)
- The test asserts the log message `Module class notExistingClass not found. Module ID notExistingClass`, but `ModuleChainsGenerator::onModuleExtensionCreationError()` only resolves the module ID when `class_exists(Module::class, false)` — **no autoload**. Run the file alone and `Module` isn't loaded yet → message says `(module id not availible)` → assertion fails. In a full-suite (or whole `tests/Unit/Core`) run, earlier tests load `Module` and it passes. Don't chase this as a regression when a single-file run shows it red.

## `RssfeedTest::testPrepareUrlSeoOff` fails in a worktree (non-8080 shop URL) — not a regression
- The test hardcodes `assertEquals('http://localhost:8080/?cl=rss...')` but `oxrssfeed::UNITprepareUrl()` reads the REAL config `sShopURL` (the mocked `getShopUrl` is ignored on this path). Git worktrees get a deterministic non-default port (e.g. `localhost:9440`), so the full unit suite shows this ONE test red with `Expected localhost:8080 / Actual localhost:9440`. It passes on the main repo (port 8080) and in CI. Don't chase it when running `./docker.sh test` from a `.claude/worktrees/*` checkout.

## A whole CLUSTER of ~14 tests false-fails in a non-8080 worktree — shop-URL / SHOPURL-env coupled, not regressions
- Running `./docker.sh test --all-failures` from a `.claude/worktrees/*` checkout (shop bound to e.g. `localhost:9240`) reliably shows **~14** red that are ALL environmental — the shop URL/host differs from CI's `localhost:8080`, or the `${O3SHOP_CONF_SHOPURL}` env placeholder isn't substituted in the worktree config. Confirmed set (2026-07-22, review of PR #192): `RssfeedTest::testPrepareUrlSeoOn/Off`; `EmailTest` order-email link tests (`testProductReviewLinksAreNotIncludedByDefaultInOrderEmail`, the 4 `...AccordingConfiguration` data sets, `testAddUserInfoOrderEmail`); `EmailUtf8Test::testSendOrderEmailToUser`; `EmailWaveTplTest::testSendOrderEmailToUser`; `ConfigTest::testGetImageDirNativeImagesIsSsl`, `testGetShopSecureHomeUrl`; `UtilsServerTest::testSaveSessionCookie`; `UtilsUrlTest::testAddBaseUrl` data sets #3/#4.
- These are the SAME on a clean branch — verify quickly with `git stash push -u && ./docker.sh test --fast <suspect files>` then `git stash pop`; the failures reproduce without your changes, proving they're not yours. CI (port 8080) is green. Don't chase them; only your feature's own tests matter from a worktree.
- ROOT CAUSE of the URL ones (fixed 2026-07-22): `.env.example` defines `O3SHOP_CONF_SSLSHOPURL="${O3SHOP_CONF_SHOPURL}"`, and `docker.sh`'s worktree block re-appended `O3SHOP_CONF_SHOPURL` at the END of `.env`. `config.inc.php` loads `.env` via `Dotenv::createImmutable`, which can't resolve a **forward reference** → `SSLSHOPURL` stayed the literal `${O3SHOP_CONF_SHOPURL}`, breaking every `getSslSelfLink()` URL (checkout/login/admin) with a "Seite ... konnte nicht gefunden werden" error. Fix: `docker.sh` now also strips + re-writes `O3SHOP_CONF_SSLSHOPURL` explicitly after `SHOPURL`. If you see a `${O3SHOP_CONF_SHOPURL}` literal in a link, check `.env` ordering / re-run `./docker.sh start`. The storefront homepage hides this (it falls back to `HTTP_HOST`); only SSL-link pages expose it.

## php-cs-fixer Cache
- `.php-cs-fixer.cache` is gitignored but speeds up repeated runs significantly. If fixer seems to miss files, delete the cache and re-run.

## String-renames break paired tests silently
- When you change a user-facing string literal in production code (error messages, log messages, "wiring pending" notices, etc.), grep the test suite for any `assertStringContainsString` / `assertSame` that still asserts on the old value. cs-fixer and static analysis don't catch this — only CI does. Common after section/task renumbers, version-string edits, copy-paste fixups.

## Audit release-eligible repos from the dep walk, not a manual list
- The o3-shop release graph has 22 release-eligible repos, not the 17 visible in `o3-shop/composer.json`'s direct `require` / `require-dev`. Five (`smarty`, `shop-doctrine-migration-wrapper`, `shop-db-views-generator`, `shop-demodata-installer`, `php-selenium`) only show up as transitive deps of `shop-ce` or `testing-library`. A manual audit will miss them. The authoritative source is `bin/release --dry-run` itself — its Step 2 walk emits every `walking o3-shop/<repo>@<branch>` line that's a release candidate. When doing org-wide work that needs to cover "all release-eligible repos" (branch protection, default-branch normalization, etc.), drive the list from a dry-run's walk output. (Discovered during the v1.6.1-RC1 dry-run; §14 had to be extended to cover the 5 missing repos.)

## CI's "Code Quality" workflow does not run the unit suite
- Lightweight PRs that touch only ReleaseTooling internals trigger only the `Code Quality` workflow on push (cs-fixer + lint), NOT the matrix `test (7.4|8.0|8.1|8.2)` workflow that runs the full suite. That means a broken test can be merged without anyone noticing. Always run `./docker.sh test-all-coverage` locally before merging anything that touches PHP — don't rely on CI to catch test failures on every branch. (PR #126 merged with `final class LiveExecutor` blocking a child stub class, and only `./docker.sh test-all-coverage` caught it on a follow-up branch.)

## Don't mark a class `final` when tests need to extend it for stubbing
- If a test file uses `extends X` to build a recording stub (test double that overrides specific methods while reusing the rest), declaring `final class X` causes a `Class Y cannot extend final class X` fatal at test-load time. Prefer `class` over `final class` for any service that has a counterpart `RecordingX` / `StubX` in the test suite. The pattern in this repo is consistent: `ReleasePlanner`, `LiveExecutor` are NOT final; their stub doubles in `ReleaseCommandTest` extend them.

## Use shop-ce's bundled composer (`vendor/bin/composer`), not PATH composer, for release tooling
- The host's PATH composer (`/opt/homebrew/bin/composer` etc.) might be 2.7+ or 2.9+ — versions with aggressive resolver-time advisory blocks. Production o3-shop installs use composer 2.2.x (the version bundled via `o3-shop/shop-composer-plugin`'s transitive `composer/composer ^1.0 || ^2.0` constraint, which resolves to 2.2.27). For pre-flight gates and any release-time composer calls, invoke `<shop-ce>/vendor/bin/composer` directly to match production behavior and avoid version-skew. `ReleaseCommand::resolveBundledComposer()` does this automatically. Discovered during the v1.6.1-RC1 cut when host composer 2.9 rejected `--no-audit` (renamed to `--no-security-blocking`) and blocked the gate; `bin/release` now uses the bundled binary via `realpath(__DIR__ . '/../../../../vendor/bin/composer')`.

## composer audit-flag rename across versions
- `composer install --no-audit` exists in 2.7-2.8 only; 2.6 lacks the audit feature entirely (and rejects the flag), and 2.9+ replaces it with `--no-security-blocking`. Don't unconditionally append audit-skip flags — bundled composer 2.2.x has no audit at all, so passing any audit-skip flag fails. Current behavior: gate uses bundled 2.2.x, no audit happens, no flag needed. If the bundle is ever upgraded past 2.6, the gate will need version-aware logic.

## Packagist sync delay after publishing GitHub releases
- Even when `gh release create` and `git push <tag>` both succeed, packagist's indexing pipeline can take ~5–60 minutes to surface the new tags in `https://repo.packagist.org/p2/<package>.json`. `composer install` against a fresh `o3-shop v1.6.1-RC1` aborted because `tinymce-editor v1.0.1` and `smarty v2.6.35` weren't yet on packagist while the other 20 cut packages had already synced. Manual fix: log into packagist.org → navigate to the package → click "Update". Auto-resolves within an hour. Workflow expectation: after `bin/release`, allow a sync window before declaring "release done."

## `composer.lock` semantics — gitignored vs committed
- `shop-ce/composer.lock` is **gitignored** (this repo's convention for libraries) — the lock that exists locally is per-developer dev-environment state, not a release artifact. The release-tooling `ComposerInstallGate` should treat gitignored locks as "skip the lock-validation gate" since the lock isn't shipped to consumers. Currently the gate skips when the lock is _absent_ (§16.6) — correct enough for fresh checkouts but doesn't catch the maintainer-side stale-local-lock case. If pre-flight ever aborts on a "your lock is stale" diagnostic on shop-ce specifically, the practical fix is `rm composer.lock && composer install` to regenerate; the gate will then skip on the absent-lock state. (After the v1.6.1-RC1 cut new tags exist with loosened constraints, fresh `composer install` regenerates a clean lock.)

## Use `dev-*` in peer-constraint pins, not `dev-<specific-branch-alias>`
- Composer reports the root package's version from a few sources, in priority order: a literal `version` field, a matching `branch-alias` for the current branch, the `COMPOSER_ROOT_VERSION` env var, or as a fallback `dev-{branchname}` (or `dev-master`/`dev-main`). Libraries that depend on shop-ce as a peer (`shop-composer-plugin`, `testing-library`, `codeception-modules`) and reference shop-ce's dev branch with `dev-dev-b-1.x` style aliases break every time shop-ce branches off a new release line — the alias goes stale immediately. **Always use `dev-*`** (the wildcard for "any dev branch") in peer-constraint pins. That accepts every git-checkout-time root version composer might report — `dev-main`, `dev-b-1.6`, `dev-feat-X`, etc. — without any maintenance per release line. Loosening to `^1.2 || dev-*` is one-time work that benefits every future release.

## Pipeline-masking: `$?` after a pipe is the LAST command's exit, not the first
- `./docker.sh test-all | tee log` then `echo $?` always reports 0 (tee succeeded), even when the inner `docker.sh test-all` exited 127 or 139. Use `${PIPESTATUS[0]}` or `set -o pipefail` to preserve the inner exit. False-green reports of "test wrapper says success when phpunit failed" almost always trace to this (filed against shop-ce as o3-shop/o3-shop#127; couldn't reproduce — the chain is correct, the trap was the report's `echo $?` reading the wrong link in the pipeline). Sentinel script `bin/check-exit-propagation.sh` asserts the chain end-to-end including real SIGSEGV.

## `docker.sh test` mangles phpunit flags like `--filter`
- `run-tests.sh` (called by `./docker.sh test`) prefixes every non-flag arg with `/var/www/html/` to make test targets work. It only recognises a small known-flag set (`--fast`, `--coverage`, `--all-failures`, `--quarantine`); anything else — including `--filter X`, `--testdox`, `--stop-on-failure` — gets path-prefixed and silently swallowed. The phpunit invocation reports "No tests executed!" with no hint that the filter was eaten. To run a single test method, either (a) run the whole test file and read the dots/F's, or (b) call phpunit directly via `docker compose exec shop php vendor/bin/phpunit --filter NAME tests/...`. The wrapper is fine for whole-file runs.

## Worktree docker needs the main repo's MariaDB up first
- `./docker.sh start` inside a worktree fails fast with `ERROR: Shared MariaDB is not running` because the docker-compose stack expects a shared db container started by the main shop-ce checkout. Run `./docker.sh start` from the canonical `shop-ce/` directory once per session before bringing any worktree containers up; you don't need a separate db per worktree.

## A pre-flight/safety gate that is silent on the pass path looks broken
- `bin/release`'s `delete_branch_on_merge` gate (#190) originally printed output only when it aborted. On the happy path (all repos already `false`) it produced zero output, so a real `--dry-run` showed nothing about the check — indistinguishable from "the check never ran." It WAS running (verified: code present, autoload maps `OxidEsales\EshopCommunity\` → worktree `source/`, all 7 merge-back repos returned `false` → silent pass; the unit test proves the path executes for a final `--to`). Lesson: any gate whose value is "it ran and everything's fine" MUST emit a confirmation line on success (header + per-target `ok` + summary), not just on failure — especially one meant to *preview* a future block in dry-run. When diagnosing "feature X doesn't run", first rule out "X runs but says nothing" before assuming a wiring bug. The merge-back set is also broader than the 3 repos issue #190 names — it's every `cut-new-tag` candidate + `o3-shop` (7 for v1.6.2), so check all of them, not just shop-ce/metapackage/o3-shop.

## Worktree container name is `o3shop-{worktree}-shop-1`, not `o3shop-{worktree}-1`
- CLAUDE.md says the per-worktree container is `o3shop-{worktree-name}-1`, but docker-compose names containers by **service**: the shop is `o3shop-{worktree}-shop-1`, plus `o3shop-{worktree}-adminer-1` and `o3shop-{worktree}-mailpit-1` (the shared db is `o3shop-shop-ce-db-1`). A `docker ps --filter name=o3shop-{worktree}-1` never matches (the `-shop-`/`-adminer-`/`-mailpit-` segment sits before the `-1`), so don't poll on that name. You rarely need the literal name anyway — `./docker.sh test*` resolves its own container. (Bit a subagent during #190; it adapted via `docker.sh`.)

## RssfeedTest hardcodes `http://localhost:8080`
- `Unit/Application/Model/RssfeedTest::testPrepareUrlSeoOn|Off` asserts against a literal `http://localhost:8080/?cl=rss&...`. Worktrees bind shop to a different port (e.g. 9390) and these two tests always fail there with an `8080`↔`9390` diff. The failure is environmental, not a regression — ignore it when reviewing test-all results from a worktree, but capture it if a real fix to RSS URL composition is intended.

## Don't ship cross-package upgrades on the same maintenance branch
- `shop-doctrine-migration-wrapper`'s `b-1.6` was carrying in-progress migrations 3.x / dbal 3.x work that anticipated shop-ce's PR #101. shop-ce v1.6.x still ships dbal 2.x. Cutting `wrapper v1.0.3` from `b-1.6` HEAD while `shop-ce v1.6.1-RC1` requires dbal 2.x produced an unsatisfiable consumer install. Resolution: preserve the dbal-3 work on a separate `b-2.0.0` branch (matches the eventual major bump when shop-ce switches to dbal 3.x), reset `b-1.6` to v1.0.2 + the §1.5 archive.exclude commit. **Pattern:** if a lib's release branch is named to match the shop's release line (`b-1.6`), don't accumulate commits there that anticipate a future major shop release. Use a separate branch (`b-2.0.0`, `feature/dbal3`) for that work and merge back to the primary line only when the shop is ready.

## Never run the shop's Symfony Console (migrations) IN-PROCESS from a composer script
- Composer executes `post-*-cmd` scripts inside its **own** PHP process, which has already loaded Composer's bundled **modern** symfony/console into the class space. The shop pins `symfony/console ^3.4` and `doctrine/migrations 2.x`. If a composer-script class builds the Doctrine Migrations `Application` in-process (e.g. `MigrationsBuilder->build()->execute()` as `Setup\Utilities` does), it gets Composer's console, not the shop's 3.4 — and doctrine/migrations 2.x command classes declare names via the legacy static `$defaultName` (no `#[AsCommand]`), which modern console ignores → `Application::add()` throws `The command defined in "…DumpSchemaCommand" cannot have an empty name`. The standalone `vendor/bin/oe-eshop-db_migrate` works because it's a separate PHP process with only the shop's autoloader. **Fix: shell out to the bins in a fresh subprocess** (pure-PHP `passthru`, no symfony in your process). This is part of the real historical reason migrations were kept out of composer. See `Core\MigrationsRunner` (#192).
- Two gotchas when shelling out to `oe-eshop-db_migrate` (`bin/migrate.php` → `Migrations::execute($argv[1], $argv[2])`):
  1. **`$argv[2]` is the EDITION filter, not a flag.** Passing `['migrations:migrate', '--no-interaction']` makes `--no-interaction` the edition; `MigrationsPathProvider::getMigrationsPath('--no-interaction')` matches nothing → returns `[]` → **every migration silently skipped, exit 0**. Pass only `['migrations:migrate']` (edition=null → all editions+modules). Non-interactivity is already hardcoded (`-n => true` in `formDoctrineInput`).
  2. **The migrate command's bundled view regeneration silently no-ops.** `Migrations::execute()` probes oxconfig with `sprintf('%s:host=…', $dbConfig['driver'], …)` where `driver` is the Doctrine name `pdo_mysql` → invalid PDO DSN `pdo_mysql:host=…` → throws → `$oxconfigReady=false` → returns 0 without regenerating views. So you MUST run `oe-eshop-db_views_generate` explicitly after migrating, or you ship a migrate-without-views half-update.
## Deleted `source/out/pictures/` tracked assets break image-URL tests
- `Unit/Application/Model/CategoryTest::testGetThumbUrl` (and other thumb/icon URL tests) assert a concrete generated picture URL like `.../category/thumb/1296_500_75/sportswear_1_tc.jpg`. If the underlying tracked source asset (`source/out/pictures/master/category/thumb/sportswear_1_tc.jpg`) is missing from the working tree, the model returns `null` and the test fails with `Failed asserting that null matches expected '...jpg'`. These picture files are committed; if `git status` shows a batch of `D source/out/pictures/...` deletions (e.g. after a disk-space cleanup), the failure is environmental, not a regression. Fix: `git checkout -- source/out/pictures/` to restore them. (Hit during #163; 83 deleted picture files made the test red — restoring fixed it and the full suite went green.)

## `./docker.sh test --fast` still runs `oe:cache:clear`, which needs a working DB
- Despite "fast (phpunit direct, no shop install)", `run_tests()` in `docker.sh` runs `php bin/oe-console oe:cache:clear` as a pre-step before phpunit. If the shop isn't fully installed (e.g. the entrypoint's non-idempotent DB import fatal-errored against a stale shared `db` container — `Table 'o3rightsroles' already exists` — and the shop container exited), cache:clear fails and the wrapper aborts with `✗ oe:cache:clear failed` *before any test runs*. For pure unit tests that need neither cache nor DB, bypass the gate by running phpunit directly in the container: `docker exec -w /var/www/html o3shop-<worktree>-shop-1 php vendor/bin/phpunit --bootstrap vendor/o3-shop/testing-library/bootstrap.php --configuration tests/phpunit.xml tests/Unit/...`. (Hit during o3-shop/o3-shop#171.)

## Shop container reports `unhealthy` transiently during a long first-run provision
- The `shop` service healthcheck is `test ! -f /tmp/o3setup-running` with `interval 5s / retries 20 / start_period 5s` (docker-compose.yml). The entrypoint (composer install + DB schema + demodata + themes) takes ~1-2 min on a first run — longer than `20 * 5s = 100s` of failing checks — so the container legitimately flips to `unhealthy` **mid-setup**, then back to `healthy` once `/tmp/o3setup-running` is removed. Any code that waits on shop readiness (e.g. `docker.sh`'s `wait_for_shop`, added for o3-shop/o3-shop#223) must treat **only `healthy` as done** and keep polling through `unhealthy` until a timeout — do NOT bail on the first `unhealthy`. (Verified during #223: a fresh worktree start showed ~20 poll dots before `healthy`.)

## `getenv()` vs `$_ENV` — phpdotenv createImmutable() only populates `$_ENV`
- `Dotenv::createImmutable()` (used in `config.inc.php`) writes values to `$_ENV` and `$_SERVER` but does NOT call `putenv()`. This means `getenv()` will return `false` for any var defined only in `.env`. Always use `$_ENV['VAR'] ?? ''` (not `getenv('VAR')`) when reading shop config env vars — consistent with how `config.inc.php` reads all other `O3SHOP_CONF_*` vars. In tests, set `$_ENV['VAR']` directly (not `putenv()`).

## An empty `sCompileDir` made OXID delete the testing-library satellite ("test_config.yml / base.php randomly disappear")
- Symptom: `./docker.sh test-all-coverage` intermittently died with `Configuration file 'test_config.yml' was not found` or `require .../base.php: No such file` (exit 255), and the coverage gate then failed with `clover report not readable: coverage/coverage.xml`. `git -C testing-library status` showed every tracked top-level file (`base.php`, `bootstrap.php`, `composer.json`, `test_config.yml.dist`, `AllTests*.php`) as `D`, plus the `testing-library/vendor` symlink gone — while `.git/`, `.gitignore`, `bin/`, `library/` survived (the fingerprint of a non-recursive `glob()`+`unlink` that skips dotfiles and dirs).
- Root cause (single bug, two symptoms): `Utils::getCacheFilePath()` did `realpath($config->getConfigParam('sCompileDir'))`. When `sCompileDir` is empty/unset, `realpath('')` returns the **current working directory**. `testing-library/base.php` does `chdir(__DIR__)`, so in the test/service bootstrap the CWD **is** the satellite. In the shop-installer *service* context (full/coverage mode only — that's why it looked "random"; `--fast`/unit runs have a valid compile dir) the shop `.env` isn't loaded, so `sCompileDir` is empty → every cache path resolved into the satellite, OXID wrote its `oxc_*` caches there, and `Utils::oxResetFileCache()`'s `glob(getCacheFilePath(null,true).'*')` + `@unlink` (delete-all-except-permanent) wiped the satellite. Losing `testing-library/vendor` then broke `test_config.yml` resolution → the "not found" symptom. Minimally-mocked `Config` in unit tests (e.g. `EmailRevocationTest`) hit the same path — before the fix they silently wrote field-name cache into the satellite (`oxc_fieldnames_o3revocation_allviews.txt`).
- Fix (source/Core/Utils.php): `getCacheFilePath()` returns `false` when the raw `sCompileDir` is empty (before `realpath`, never falling back to CWD); the three `oxReset*Cache()`/`resetLanguageCache`/`resetMenuCache` callers guard `$path ? glob($path.'*') : false` (else `glob(false.'*') === glob('*')` still globs CWD); and the write paths degrade gracefully — `_lockFile()` returns false for an empty path (no `fopen('')` → PHP 8 `ValueError: Path cannot be empty`) and `setLangCache()` skips when the path is false. Regression tests in `tests/Unit/Core/UtilsTest.php`.
- Recovery if it already happened: `git -C testing-library checkout -- .` restores tracked files; `ln -sfn ../vendor testing-library/vendor` recreates the deleted symlink (a bare `./docker.sh stop && start` does NOT — the entrypoint sees `testing-library/.git` and skips the re-clone, leaving the gutted tree). `test_config.yml` at the shop root is generated by composer's Incenteev `post-install-cmd` and is gitignored in the satellite.
- Lesson: an unconfigured path must never silently become "the current directory". `realpath('')`/`realpath(null)` == CWD is a footgun anywhere a glob+unlink or file write follows. Related: the satellite-symlink layout in `docker/entrypoint.sh` (`vendor/o3-shop/testing-library` -> `../../testing-library`, plus `testing-library/vendor` -> `../vendor`) means `realpath()`/`__DIR__` math resolves *into* the satellite.
## The mod_rewrite self-probe runs during Setup BEFORE a DB exists — never read DB-backed `Config` there
- `SystemRequirements::checkModRewrite()` / `_getModRewriteResponse()` run during the Setup wizard's **System Requirements** step (`STEP_SYSTEMREQ=100`), which is *before* `STEP_DB_INFO=400` — i.e. before the user has entered DB credentials and before any schema exists. In that context `isAdmin()` is `false`, so the host info comes from `$_SERVER` (no Config), and NOTHING in this path may touch the DB. Calling `Registry::getConfig()->getConfigParam('x')` there is a trap: `Config::getConfigParam()` → `init()` → `initVars()` → `_loadVarsFromDb()`, and `initVars()` **throws `DatabaseException`** when the `oxconfig` table is empty/absent → `_handleDbConnectionException()` swaps in the offline page (or rethrows in debug/CLI) → the System Requirements page breaks for **every fresh install**. To read a `config.inc.php` value in any Setup-time code path, use the DB-less `ConfigFile`: `Registry::get(\OxidEsales\Eshop\Core\ConfigFile::class)->getVar('x')` (returns null if unset → cast to bool = false). `checkServerPermissions()` in the same class already reads `sCompileDir` this way for exactly this reason. In unit tests, drive such a flag via `Registry::get(ConfigFile::class)->setVar(...)`, not `getConfig()->setConfigParam(...)`. (Caught in o3-shop/o3-shop#27 self-signed-cert work by the final whole-branch review; the per-task reviews missed it because the unit tests run against an already-installed shop where `Config::init()` succeeds.)

## A database migration runs WITHOUT the shop bootstrap — no `oxNew()`, no `Registry`
- `vendor/bin/oe-eshop-db_migrate` / `oe-eshop-doctrine_migration` boot only the composer autoloader + the migration wrapper. `source/bootstrap.php` is never included, so `oxfunctions.php` is absent and **`oxNew()` is undefined**. Anything reaching `Registry::getX()` from a migration dies with `Call to undefined function oxNew()`. That is why no migration in this repo has ever cleared a cache or touched a model.
- What IS available and safe to use inside a migration: `new \OxidEsales\Facts\Facts()` (→ `getSourcePath()`), `new \OxidEsales\EshopCommunity\Core\ConfigFile(<source>/config.inc.php)` (→ `getVar('sCompileDir')` etc., no bootstrap needed), plain Doctrine, and **static** methods on `EshopCommunity\` classes (a static call loads the class without running a constructor). Reference the `EshopCommunity\` class directly, never the `OxidEsales\Eshop\` unified-namespace alias.
- `postUp()` / `preUp()` ARE invoked — `Version/Executor.php` calls them dynamically as `$migration->{'post' . ucfirst($direction)}($toSchema)`, so grepping for `postUp(` finds nothing but the declaration. Wrap their bodies in try/catch: the schema change has already been applied when they run, so a failure there must not abort the migration.
- Adding a column is NOT enough for the model to see it: the `<table>` field-name cache under `source/tmp/` is permanent (`Utils::$_sPermanentCachePattern`; `oxResetFileCache()` inverts the pattern and keeps it). Call `Utils::clearTableFieldCacheIn($compileDir, $table)` — the dependency-free static counterpart added for o3-shop/o3-shop#226 item 1 — from `postUp()` for every table whose columns changed, else the feature is silently inert on any shop upgraded with a warm tmp dir. Verified end to end by re-running a migration: 4 `oxarticles` entries cleared, `oxorder` untouched.

## `InternalShimCallSitesTest` exclusions are anchored by file + LINE — any insertion breaks the gate
- `tests/Unit/BackwardsCompatibility/internal-shim-call-sites-exclusions.json` keys each allowed call site on `{file, line}`. Insert or delete lines anywhere above an excluded call and the gate test fails with "N internal call-site convention violations found" listing call sites you never touched (hit in #226: 9 pre-existing `Article.php` `getPrice`/`getVarMinPrice`/`getAmountPriceList` entries went stale after edits higher up the file).
- Fix by re-anchoring, not by adding new exclusions: the relative ORDER of call sites inside a file is insertion-invariant, so map old→new entries by position, and assert `"\$this->{$method}("` actually appears on the new line before writing. Write the JSON back with `indent=4` to avoid reformatting the whole file. Never "solve" this by deleting exclusions — that hides real violations.

## `./docker.sh test --fast` with MULTIPLE paths silently runs only the FIRST one
- `./docker.sh test --fast tests/Unit/Core/UtilsTest.php tests/Unit/Core/Guarantee/ tests/Unit/Application/Model/ArticleGuaranteeTest.php` reported `OK (82 tests, 219 assertions)` — byte-identical to running `UtilsTest.php` alone. The other two paths never executed. There is no warning; a green bar looks exactly like full coverage of everything you listed.
- **How to spot it:** compare the test count against the sum of the individual files. If it equals the first path's count exactly, the rest were dropped.
- **How to apply:** run one path per invocation in a shell loop (`for f in …; do ./docker.sh test --fast "$f"; done`) and read each result, or just run the full suite. Never claim "all touched tests pass" from a single multi-path invocation. (Caught in the PR #218 review round: three suites I believed I had run had not been.)
## `OX_BASE_PATH` cannot reach `Core/`, `Internal/` or the blacklisted `Application/` subtrees on a composer install
- `OX_BASE_PATH` is the **shop's** `source/` dir (`bootstrap.php`: `INSTALLATION_ROOT_PATH/source/`). On a composer install, `ShopPackageInstaller::copyShopSourceFromPackageToTarget()` copies the *package's* `source/` into it while applying `composer.json` → `extra.oxideshop.blacklist-filter`, which currently strips `Application/Component/**`, `Application/Controller/**`, `Application/Model/**`, `Core/**` and `Internal/**` — those classes are autoloaded straight from `vendor/` instead. So `OX_BASE_PATH . 'Core/…'` resolves to a path that **does not exist** on a composer-installed shop.
- A git checkout hides this completely: package root == project root, so the path happens to work. Only a composer-installed shop shows the breakage, which means the dev unit suite structurally *cannot* turn red for it — both expressions produce the identical string in a checkout.
- **Rule:** any non-PHP asset that ships next to its class (artwork, fonts, fixtures) must be addressed relative to the class file via `__DIR__`, never through `OX_BASE_PATH` or `sShopDir`. `source/out/**` and `source/Application/views/**` *are* copied, so those are safe to reach via `OX_BASE_PATH`. `bootstrap.php:205` shows the pre-existing precedent (`is_dir(OX_BASE_PATH.'Core')` → fall back to `Facts::getCommunityEditionSourcePath()` for `CORE_AUTOLOADER_PATH`).
- Guard: `tests/Unit/Core/ComposerBlacklistedAssetPathTest.php` scans `source/**/*.php` for `OX_BASE_PATH . '<literal>'` and fails if a literal lands in a blacklisted subtree, evaluated with the plugin's own `GlobMatcher` against the real filter. Extend it rather than re-deriving this.
- Real incident (2026-07-28): `GuaranteeLabelGenerator::getAssetDir()` used `OX_BASE_PATH . 'Core/GuaranteeLabel/assets/'`, so every composer install logged `Label template '…/source/Core/GuaranteeLabel/assets/nested-template.png' is missing` and rendered no EU guarantee label. Fixed to `__DIR__ . '/GuaranteeLabel/assets/'`. Note the templates/fonts live under `Core/` on purpose (not web-served); the `notice-*.png` artwork lives under `out/pictures/guarantee/` and was never affected. Related: [[reference_eu-guarantee-labels]].
- Aside found in the same sweep, deliberately left alone: `Core/Email.php` calls `setLanguage('en', sShopDir . '/Core/phpmailer/language/')` — a directory that exists in no layout. PHPMailer falls back to its built-in English, so behaviour is already correct.

## A "lightweight" partial SELECT into `ArticleList` saves nothing — `Article` lazy-loads the rest, one query per row
- `Article` sets `$_blUseLazyLoading = true` (source/Application/Model/Article.php:85). `BaseModel::__get()` (source/Core/Model/BaseModel.php:294) intercepts any `oxarticles__<field>` that was NOT in the SELECT and, if `getId()` is set, runs a `select *` for that oxid (cached per object in `_aInnerLazyCache`). So hand-rolling `SELECT oxid, oxtitle, oxprice, oxthumb FROM …` and then calling `getPrice()` / `getThumbnailUrl()` / `getLink()` costs **one extra full-row query per list item** on top of the list query — the partial select is strictly worse than `$oArticle->getSelectFields()`.
- The trap is silent: values come out correct (that's the lazy loader doing its job), so nothing fails in tests — only the query count grows. `getPrice()` alone reaches `getArticleVat()` → `getCustomVAT()` → `oxarticles__oxvat`, i.e. any price display triggers it.
- **How to apply:** for article lists either select `getSelectFields()` (one query, model fully usable) or skip the model entirely and use `DatabaseProvider::getDb()->getAll()` on plain rows. Never invent a "slim" article select and then call model getters on it. Spotted reviewing PR #219 (`Search::getSearchSuggestions()`).
